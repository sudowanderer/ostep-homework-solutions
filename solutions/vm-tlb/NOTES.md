# vm-tlb — TLB 对访问延迟的影响

书本章：[Paging: Faster Translations (TLBs)](http://www.cs.wisc.edu/~remzi/OSTEP/vm-tlbs.pdf)（第 19 章）

这个目录只有测量程序 `tlb.c`。它按「每页碰一个 int」去扫内存，看页数变多、TLB 装不下时，程序每次访问要多花多少时间。

## tlb

- **目标：** 把 TLB 命中和 TLB 压力从普通的内存访问里分离出来。页数少时，地址翻译打在最快的 TLB 上；页数超过那一级 TLB 能装下的项数后，同一次 `a[i] += 1` 会变慢。
- **编译：**

```sh
cd solutions/vm-tlb
gcc -O2 -o tlb tlb.c
```

- **运行：**

```sh
./tlb <pages> <trials>
```

`pages` 是这次要碰到的不同页数，`trials` 是把这些页重复扫多少遍。程序打印页大小、总访问次数，以及平均每次访问的纳秒数。

例如只碰 32 页、重复 250 万遍：

```sh
./tlb 32 2500000
```

页数从 1 加到几万、每次大约翻倍，可以用：

```sh
for p in 1 2 4 8 16 32 64 128 256 512 1024 2048 4096 8192 16384 32768 65536; do
  trials=$((80000000 / p))
  if [ "$trials" -lt 10000 ]; then trials=10000; fi
  ./tlb "$p" "$trials"
done
```

单次访问只有零点几纳秒到几纳秒，短于一次计时调用本身。`pages * trials` 要到千万次以上，再用总时间去除，纳秒级的差别才稳得住。上面这个循环把总访问次数维持在大约 8×10^7；页数很大时把 `trials` 降到 10000，避免一次扫描跑太久。

## 循环为什么能测到 TLB

每次只在一页里写一个 `int`，下一次访问跳过整整一页：

```c
long jump = page_size / sizeof(int);   /* 本机 page_size = 16384，jump = 4096 */
for (long t = 0; t < trials; t++) {
    for (size_t i = 0; i < num_ints; i += jump)
        a[i] += 1;
}
```

这样页数直接等于这次要用到的 TLB 项数。真正写下的数据只有每页 4 字节，数据缓存的压力远小于 TLB 的压力。时间随页数上升，主要来自地址翻译，而不是把一大块数组读进缓存。

计时用 `clock_gettime(CLOCK_MONOTONIC)`，包住上面的两层循环。`ns/access = 总时间 / (pages * trials)`。

另外两处是为了不把 TLB 以外的成本算进去：

- `calloc` 之后先把每一页写一遍再开始计时。第一次碰到匿名页会缺页、做 demand zeroing，那个成本比 TLB miss 大得多。预热把它移出计时区间。
- 计时结束后把每个碰过的元素加进 `checksum` 并打印。`-O2` 仍会生成真正的 `ldr` / `add` / `str`（夹在两次 `clock_gettime` 之间），不会把「结果没人读」的循环删掉。

本机页大小是 **16384 字节**（Apple Silicon），不是书里常见的 4096。同样多的 TLB 项，能覆盖的虚拟地址是 4KB 页机器的 4 倍。看拐点时看页数，不要拿书上的页数直接对比。

## 本机一次扫描

## 怎么读这张表

1 到 8 页大约 0.3–0.6 ns/access。这些页能放进最快的那级 TLB，数据也在 L1。只碰 1 页时，每次都是对同一个 `int` 做 load-add-store，前后有依赖；2–8 页时不同页互不依赖，CPU 可以把多次访问重叠起来，所以平均时间更低。

12 页开始明显变慢，32 页附近到大约 **10 ns/access**，大约是 8 页时的 30 倍。工作集刚超出最快 TLB 时，每次 `a[i] += 1` 都要到更慢的一级去做地址翻译。这是这次实验里 TLB 对程序最清楚的影响。

64 页以后回到大约 5–6 ns，一直到 16384 页都差不多。步长是固定的一整页，页数一多，硬件可以顺着这个规律提前准备后面的翻译。页数只有十几、二十几、循环又马上折返时，这种提前准备帮不上忙，所以 16–32 页反而是这次扫描里最慢的一段。书上的示例图在超出 TLB 之后会台阶式停在一个更高的 miss 代价上；这台 M3 上，顺序扫页时后面的硬件把大部分 miss 藏起来了，曲线会先冲高再落回平台。

32768 页大约 7.4 ns，65536 页大约 8.4 ns。这里虚拟跨度已经到 512 MB–1 GB，但每页仍然只写 4 字节。上升比较缓，是更大的 TLB 和页表遍历开始跟不上，缺页不在计时里面（预热已经把页建好了）。

绝对纳秒数包含循环本身、load、store，还有当时 CPU 频率，不是「一次纯 TLB miss 的延迟」。换机器、系统忙、或者进程被调度到能效核上，数字都会变。要保留的是形状：页数跨过最快 TLB 的容量时，同一种访问会慢一个数量级。

## 测量时还要注意的事

- **计时器精度。** 这里用的是 `CLOCK_MONOTONIC`，不是 `gettimeofday()`。不管哪一个，单次页访问都远短于「能单独量出来的一次调用」。可靠做法是大量重复再取平均。同一页数连跑 3 次，上面 8–256 页的结果能对上，说明 8×10^7 次访问在这台机器上够用。
- **不要绑核时的误差。** 每个 CPU 有自己的 TLB。macOS 没有 `sched_setaffinity`，这个程序也没有把线程钉在一个核上，调度器可以在性能核和能效核之间迁移。两套 TLB 的容量和速度不一样，混在一次计时里会把拐点抹平。这次重复结果还比较稳；如果曲线突然乱跳，先怀疑是跑到了不同的核上。
- **编译优化。** 作业提醒编译器可能删掉「只做 `+= 1`、结果没人用」的循环。这个程序靠最后的 `checksum` 把结果用掉，并用 `-O2` 编译。检查过生成的汇编，计时区间里的内层循环仍是按 `jump` 跨步的 load-add-store。
